# VideoMind 技术面试讲解

## 30 秒介绍

VideoMind 是支持长视频分析的 AI 视频工作台。它把视频、ASR/OCR 时间轴、证据检索和 AI 回答放在一个界面中。用户点击答案级引用，可以回到被验证的来源记录和视频时间点。后端把视频转为分段时序上下文，经检索后交给 Planner、Executor、Critic，并在模型调用前检查累计预算。

## 2 分钟介绍

产品问题是：长视频的信息散布在语音、画面文字和不同时间位置，普通聊天界面很难证明回答来自哪里。VideoMind 先用 FFmpeg、Whisper 和 Tesseract 提取带时间戳的 ASR/OCR，建立以 `VideoContext` 为权威来源的时间窗口与逐条观察。五分钟分块和 Embedding/关键词混合检索先缩小候选范围；Planner 制定任务，Executor 产生分析，Critic 检查结果。最终应用层校验来源身份、文本与时间覆盖，只有绑定成功的 Evidence 才能形成可点击引用。

界面由 Vue 3 提供媒体库与分析工作台，FastAPI 提供 REST/SSE；Celery 与 RabbitMQ 处理异步任务，MySQL 保存持久记录，Redis 保存运行态，MinIO 保存媒体，Qdrant 建立向量索引。执行预算跨请求与重试累计，在每次 HTTP 模型调用前准入；逐阶段遥测区分供应商报告用量与估算。项目保留一次失败的正式路由实验：80/80 结果完整，但预注册质量门槛没有通过，因此没有宣称自适应路由更优。

## 核心技术难点

1. **长视频上下文**：全量转录直接入 Prompt 会重复传递大量元数据。时间窗口和分块支持全片定位，检索挑选相关区域，角色各取所需投影。Planner 看粗窗口，Executor/Critic 看精选的逐条来源文本。
2. **统一时间模型**：ASR 的原始时间段和 OCR 的采样帧进入同一 `VideoContext`，但保留各自来源身份与粒度。60 秒窗口适合全局浏览；逐条 observation 用于精确定位，二者用途不同。
3. **证据可信度**：模型引用请求只是候选。确定性校验会核对来源 ID、原文和时间范围；无法绑定的条目不能冒充可信引用。当前界面提供答案级，不承诺逐句归因。
4. **Agent 分层**：Planner 规划、Executor 执行、Critic 给出语义反馈；应用代码校验 DTO、工具授权和 Evidence 不变量。Critic 的判断不替代确定性检查。
5. **交互闭环**：引用携带可解析的来源与时间范围；界面展开 Evidence，定位时间轴，再驱动浏览器播放器 seek。
6. **预算与可观测性**：每次模型调用前进行累计 token 准入，重试沿用账本。实际 usage 优先；缺失时标注估算来源，不能把预留额度当作实际供应商费用。
7. **持久性**：MySQL 中的执行记录是历史事实；checkpoint 支持恢复，Redis 是运行投影。历史 replay 不重新调用模型或检索器。

## 一条工程演进主线

早期做法让多个阶段直接接收大块上下文，其中包含重复的来源表示。问题是 Prompt 膨胀、token 预算超额，而且压缩上下文后曾出现“分析完成但零条可绑定引用”。最终路径保留权威 `VideoContext`，按阶段构造精简投影，同时给 Executor/Critic 提供足以绑定来源的精确行；在模型调用前做预算准入，模型输出后做确定性 Evidence 校验。取舍是需要维护两类投影和清晰的来源映射，但避免为节省 token 而丢失可信引用。

## 面试官可能追问

**大文件上传如何续传和收敛？** UUID 标识一次上传尝试，内容哈希标识文件内容，两者分开。
浏览器按 5 MiB、并发 3 上传，只保存按用户隔离的 uploadId；续传查询服务端确认的分片索引。
Redis 保存约 24 小时的会话和分片 Set，MinIO 保存分片字节。先写对象，再原子确认 Set 和续期，
Redis 确认失败保留对象，重传同一确定性分片键即可恢复。

**合并锁是否等于幂等？** 不等于。每个 uploadId 的 redis-py 分布式锁避免多个后端同时合并；
独立的完成回执 uploadId → mediaId 让后续重复请求和丢失响应重试返回同一结果。
锁租期 30 分钟，合并期限 20 分钟，使用客户端库的 token 校验与边界续期，没有定时 watchdog。
顺序合并时增量计算内容哈希，最终对象在 MinIO，持久媒体元数据在 MySQL。

**MySQL 已提交，但 Redis 回执失败怎么办？** 返回可重试错误，保留持久记录、最终对象及有效分片。
最终对象来源按 UUID 确定；下次 complete 在锁内按该来源找到已提交记录，重建回执并返回同一 mediaId，
不再次合并或新增记录。回执和真实媒体记录都校验用户所有权。成功后清理失败只留下临时对象，
不会撤销业务成功。恢复受会话/回执 TTL、持久记录存在和 Redis 锁可靠性约束，不宣称 exactly-once。
完整审计和真实 Redis/MinIO/MySQL 测试见 [上传收敛报告](UPLOAD_FINALIZATION_REPORT.md)。

**为什么不把 ASR/OCR 再持久化成第二套权威表？** `VideoContext` checkpoint 已经保存权威时序来源。额外的权威副本会引入同步和身份漂移；分页 API 从既有来源投影读取。

**为什么是答案级引用？** 后端能验证答案所列 Evidence 的来源和时间覆盖，但不能证明每个自然语言句子都与单一片段一一对应，所以界面只承诺可验证的粒度。

**为什么 Critic 后还需要 Evidence Guard？** Critic 的语义判断可能波动；来源存在性、文本匹配、时间覆盖与工具权限必须由应用代码落实。

**为什么保留浏览器原生视频控件？** 产品核心是来源联动，原生控件已具备可靠播放与 seek 能力，避免重复实现播放器复杂性。

**为什么保留 `DOVIDEO_*`？** 它是现有部署、脚本和测试使用的配置接口。品牌改为 VideoMind 不应迫使用户迁移环境变量。

**50k token 预算是否保证账单上限？** 不保证。它是累计 token 准入策略；输入估算和输出预留不是上游最终 usage，供应商价格与隐式推理消耗也会变化。

**这个项目证明自适应路由更好吗？** 没有。X3 的 80 个结果均持久化，但没有一条通过预注册质量门槛；两个路由臂都选了 BALANCED。该实验给出边界清晰的负面结果。
